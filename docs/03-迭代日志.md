## 基线 1 · 2026-09-26 · hash 兜底向量

**配置**

| 项 | 值 |
|---|---|
| 语料 | 2 份合成示例条款（21 个 chunk） |
| 切分 | max_chars=800, min_chars=60，开启层级路径注入 |
| Embedding | `hash`（字符 n-gram，dim=512）—— **兜底方案** |
| 检索 | top_k=20 / top_n=5，RRF k=60，无 Rerank |
| LLM | `mock` |

**结果**

| 模式 | Hit Rate | MRR | 全部命中 |
|---|---|---|---|
| vector | 100.00% | 0.8584 | 100.00% |
| keyword | 100.00% | 0.9583 | 100.00% |
| hybrid | 100.00% | 0.9236 | 100.00% |

**⚠️ 关键判断：这组数字是无效的，不能用来证明系统做得好。**

理由（**这一条是整份日志里最有价值的内容，面试可以直接讲**）：

1. **语料太小**：只有 21 个 chunk，30 道题的答案几乎一一对应到某个块，
   top-20 召回等于"把库里大半的东西都捞回来了"，**Hit Rate 必然接近 100%**。
2. **测试集被语料规模限制**：题目是照着我写的示例条款出的，答案原词
   （"90日""1万元""120种"）**直接出现在正文里**，连字符 n-gram 都能命中。
3. **hash 向量不是语义向量**：它衡量的是字形重叠，不是语义相似。
   它能区分"等待期"和"保险责任"（字不同），
   但**识别不了"理赔要多久"和"赔付时效"是同义**——而那正是向量检索的价值所在。

**结论**：这一轮只证明**链路是通的**（加载→切分→向量化→检索→生成→评测全部跑通），
**不构成任何效果结论**。

**下一步（按优先级）**

1. ~~语料扩到 3–5 份真实条款，chunk 数上到 150+~~ →
   **不够**。真正的分界线是**让答案不再等于原词匹配**：
   题目要问得"绕"，比如"我住院花了 8 万，社保报了 5 万，能赔多少"——
   需要跨"免赔额 + 赔付比例 + 社保抵扣"三条计算。
2. 换**真实 embedding**（`api` 或 `local`），这是拿到有效数字的前提。
3. 换**真实 LLM**，才能评生成层。
4. 加**干扰语料**：把不相干的条款也放进库，看检索会不会被带偏
   （现在库里只有 2 个产品、9 条条款，检索难度被人为降低了）。

## 一个真实的 bug 记录（第一个坑）

**现象**：`detect_heading("1.1 保险责任")` 返回 `None`，数字编号标题识别不出来。

**排查**：看代码发现列表项规则 `_LIST_ITEM_RE` 在编号规则之前执行。
`_LIST_ITEM_RE` 的第一个字符类 `[一二三四五六七八九十\d]` 后面跟 `[）)、.．]`，
所以 `"1.1 保险责任"` 里的 `"1."` 被当成列表项**抢先匹配**，直接 return None。

**解决**：把数字编号标题的判断**提到列表项规则之前**。
顺序很重要——两个规则的字符集有重叠，谁先谁后决定结果。

**测试**：在 `tests/test_chunker.py::test_detect_numbered_heading` 里固化这个用例。

> **面试价值**：这是一个"看起来小、但会让整份 PDF 条款的层级结构全乱"的 bug。
> 讲它能证明你真的调过、而不是照着教程抄的。
