# 保险条款 RAG —— 技术方案（对外可讲版）

> 项目定位：一份**能上线演示、能讲清每个决策、有量化评测**的 RAG 应用。
> 目标读者：你自己（照着做）、面试官（照着讲）。

---

## 0. 一句话定义

**把一份或几份保险条款变成可问答、可对比、可溯源的知识库，并给出结构化的核保结论。**

比"RAG 问答"多出来的部分，才是这个项目的价值：**结构化字段提取 + 跨条款聚合 + 引用溯源**。

---

## 1. 为什么保险条款是"好 RAG 语料"（面试第一问的答案）

| 特征 | 保险条款 | 普通文档 |
|---|---|---|
| 关键信息位置 | **埋在正文深处**（等待期 90 天、免赔额 1 万） | 常出现在摘要/首段 |
| 结构 | **天然编号**（第X条 / X.X / （一）） | 连续散文 |
| 答案判定 | **答案就是条款原文，客观可验证** | 主观、模糊 |
| 聚合需求 | **强**（"赔不赔"要同时看保险责任+免责+等待期+免赔额） | 弱，单点事实为主 |

→ **推论**：这类语料能逼出真实的"切分不当导致召回错误"问题，**面试时你有真实的坑可讲**——这是论文/博客类语料给不了的。

## 2. 数据层

### 2.1 支持格式

| 格式 | 说明 |
|---|---|
| **JSON（推荐）** | 你自己整理的条款结构化数据（`data/raw/*.json`），字段见 2.2 |
| PDF | 通过 `pypdf` 抽取文本；**仅支持文本型 PDF**，扫描件需 OCR（本期不做） |
| 纯文本 / Markdown | 直接走通用递归切分 |

> ⚠️ **为什么把 JSON 设为首选**：真实条款 PDF 里大量是表格（现金价值表、保障责任表），`pypdf` 抽出来是乱的。用 JSON 可以让"语料质量"和"解析难度"解耦——**先把检索跑通，再回头啃 PDF 解析**。

### 2.2 JSON 语料 Schema

```json
{
  "doc_id": "pingan-e-shengbao-2024",
  "product_name": "平安e生保长期医疗险",
  "company": "平安健康保险股份有限公司",
  "version": "2024版",
  "doc_type": "百万医疗险",
  "effective_date": "2024-01-01",
  "sections": [
    { "level": 1, "title": "第一部分 总则", "children": [
        { "level": 2, "title": "第一条 保险合同的构成",
          "text": "本保险合同由保险单、保险条款……" }
    ]}
  ]
}
```

- `level` 必须准确 → **它决定切分的父子结构**
- `text` 里可以带 `\n`，段落之间用空行

## 3. 切分层：整个项目最关键的一步 ⭐

### 3.1 核心决策：**不按字数切，按条款层级切**

**基线做法（要能说出它错在哪）**：
```
按 500 字固定窗口切，重叠 50 字
```

**它会出的问题**（复试必问）：
1. **切断语义单元**：把"等待期"和"保险责任"切进不同块，检索返回半句话
2. **丢失上下文**：一个 chunk 只有"90 天"，不知道是哪种病的等待期
3. **条款编号丢失**：无法引用、无法溯源

### 3.2 本项目的做法：**层级感知切分（Hierarchical Chunking）**

```
文档
 └─ 第一部分 总则           ← level 1
     └─ 第一条 保险合同的构成   ← level 2  ←【默认 chunk 边界】
         ├─ 正文段落
         └─ （一）……          ← 列表项，并入父块，不单独切
```

**规则**：
| 规则 | 做法 | 为什么 |
|---|---|---|
| 基本单元 | **以"条"为一个 chunk** | 条款是法律意义上的最小完整单元 |
| 上下文注入 | 每个 chunk 头部拼上父级路径：`【产品】>【第X章】>【第X条】` | 让孤立片段自带上下文，显著提升召回 |
| 超长处理 | 单条超过 `max_chars`（800）→ 按 `（一）（二）` 列表项二次切分，并保留条标题 | 避免上下文窗口浪费 |
| 过短合并 | 单条少于 `min_chars`（60）→ 与**相邻同级**条款合并 | 避免"第X条 定义"这种碎片块 |
| 列表项 | `（一）` `1.` 等**不作为独立 chunk 边界** | 它们是条款内部结构，切开就丢主语 |

### 3.3 每个 chunk 携带的元数据（决定"能不能溯源"）

```python
{
  "chunk_id": "pingan-e-shengbao-2024#c0012",
  "doc_id": "pingan-e-shengbao-2024",
  "product_name": "平安e生保长期医疗险",
  "doc_type": "百万医疗险",
  "section_path": ["第三部分 保险责任", "第六条 保险责任"],
  "article_no": "第六条",
  "article_title": "保险责任",
  "text": "【平安e生保长期医疗险 > 第三部分 保险责任 > 第六条 保险责任】\n……",
  "raw_text": "……",
  "char_len": 412,
  "has_table": false
}
```

> **面试点**：`section_path` 注入到 `text` 里这一步，本质是**用工程手段补偿向量检索丢失的结构信息**。这就是"上下文工程"，不是"调模型"。

## 4. 向量化层（Embedding）

### 4.1 可插拔设计（这是被环境逼出来的正确架构）

| Provider | 依赖 | 用途 |
|---|---|---|
| `api` | `requests` | **生产用**：OpenAI 兼容接口（DeepSeek / 智谱 / 通义 / 硅基流动 / 本地 vLLM） |
| `local` | `sentence-transformers`（需 PyTorch） | 数据不出内网的场景。**模型推荐 BGE 中文系列**（`BAAI/bge-large-zh-v1.5`） |
| `hash` | 无 | **零依赖兜底**：字符 n-gram 哈希。只为让全链路可跑，效果很差 |

> ⚠️ **必须诚实**：`hash` provider 是"能跑通"级别的占位，**不是"能用"级别**。用它做的评测数据没有意义。
> **要拿到简历上能写的数据，必须换成 `api` 或 `local`。**

### 4.2 一个常被忽略的坑

**换 embedding 模型必须重建整个索引**——向量空间变了，新旧向量不可比。所以：
- 索引文件里必须存 `embedding_provider` + `model_name` + `dim`
- 加载时校验，不一致直接报错，**而不是静默返回垃圾结果**

## 5. 检索层：混合检索 + 重排

### 5.1 为什么纯向量不够

| 查询 | 纯向量的问题 | 混合检索怎么救 |
|---|---|---|
| "第六条怎么写的" | 向量不擅长**精确编号匹配** | **BM25 关键词**直接命中"第六条" |
| "甲状腺结节能赔吗" | 条款用的是"既往症""特定疾病"，**字面无重叠** | 向量负责语义 |
| "免赔额一万" | 数字匹配弱 | BM25 精准 |

→ 所以：**向量检索（语义）+ BM25（关键词）+ RRF 融合 + 可选 Rerank**

### 5.2 RRF 融合（不用调权重，工程上最稳）

```
score(d) = Σ_over_retrievers  1 / (k + rank_i(d))     k 取 60
```
只依赖**排名**不依赖分数尺度 → 两个检索器的分数量纲不同也不怕。

### 5.3 Rerank（第二阶段，必做）

- 一阶段召回 `top_k=20`（要广度）
- Rerank 后取 `top_n=5` 送进模型（要精度）
- 实现可选：BGE-reranker（本地）/ Cohere / 或用 LLM 直接打分（贵但简单）

### 5.4 元数据过滤（为"多产品对比"铺路）

先按 `doc_id` / `doc_type` 过滤，再做向量检索 → 这是**结构化约束 + 语义检索**的组合，
也是为什么真实系统里"向量库"从来不是唯一组件。

## 6. 生成层：把"幻觉"当工程问题管

### 6.1 系统提示词必须包含的四条硬约束

```
1. 只依据【检索到的条款片段】回答，不得使用外部知识
2. 每个结论后面必须标注来源：【产品名 第X条】
3. 检索片段中没有相关信息时，回答"根据现有条款无法确定"，并说明缺什么
4. 涉及"是否赔付"的判断，必须列出依据的多个条款，不能只引用一条
```

### 6.2 结构化输出（对应面试题 Q12）

强制返回 JSON：

```json
{
  "answer": "……",
  "citations": [{"doc_id": "...", "article_no": "第六条", "quote": "……"}],
  "answerable": true,
  "used_articles": ["第六条", "第九条", "第十二条"]
}
```

**四层保障**（缺一层就会在演示时翻车）：
1. 提示词给 schema + 一个完整示例
2. 请求里开 JSON mode（供应商支持的话）
3. 代码层用 `pydantic` 强校验 → **不信任模型输出**
4. 校验失败 → 把错误回填重试（最多 2 次）→ 仍失败则降级为纯文本答案

### 6.3 流式输出（JD 里"接口联调"的核心）

- 后端：`StreamingResponse` + SSE，`media_type="text/event-stream"`
- 前端：`fetch` + `ReadableStream` 逐块解析
- **两个必须处理的细节**：
  - **引用要和正文分开传**（引用在生成结束后一次性给，不要混进 token 流）
  - **中途断开要有兜底**（用户点"停止"，后端要能取消）

## 7. 评测层（区分"玩具"和"项目"的分水岭）⭐

### 7.1 分两层评，不能混着评

| 层 | 指标 | 怎么算 |
|---|---|---|
| **检索层** | Hit Rate@k、MRR | **自动化**：测试集标了"答案在第几条"，看有没有召回 |
| **生成层** | 答对率、拒答准确率、引用正确率 | LLM 评审 + 人工抽查 |

> **为什么必须分开**：答错了到底是"没检索到"还是"检索到了但模型胡说"？**分不开就没法定位问题。**
> 这句话在面试里很加分。

### 7.2 测试集构造（30 题，四类）

| 类型 | 数量 | 例子 | 考察点 |
|---|---|---|---|
| **A 单条事实** | 10 | "等待期是多少天？" | 基础检索准确性 |
| **B 跨条款聚合** | 8 | "甲状腺结节住院能赔吗？"（需同时看 责任+免责+既往症定义+等待期） | **多跳能力，最难** |
| **C 应拒答** | 6 | "这份保险的保费是多少？"（条款里没有，在费率表里） | **幻觉治理，最能体现成熟度** |
| **D 多产品对比** | 6 | "A 和 B 哪款对结节更友好？" | 跨文档 + 结构化输出 |

每题字段：
```csv
qid,type,question,expected_answer,expected_doc_ids,expected_articles,notes
A01,fact,等待期是多少天?,90天,pingan-e-shengbao-2024,第三条,
```

### 7.3 关键做法：改一次，跑一次

每改一次切分策略 / Top-K / Rerank / 提示词，**重跑全部 30 题并记录**。
`docs/03-迭代日志.md` 里的数据就是这么来的——**那就是你面试时的弹药**。

## 8. 部署

| 项 | 方案 |
|---|---|
| 打包 | Dockerfile（`python:3.12-slim`，**不用 3.14，很多库没轮子**） |
| 服务 | `uvicorn` 单进程起步；后续 `--workers` |
| 配置 | `.env` 注入 API Key，**绝不进 git** |
| 日志 | 记录每次问答的 query / 召回 chunk_id / 引用 / 延迟 |
| 缓存 | 相同问题缓存答案（省钱 + 降延迟，**这是最容易被问到的优化点**） |

> **你本机没有 Docker**（已确认）。所以：本地用 `uvicorn` 直接跑，Docker 只在最后打包阶段验证（可以装 Docker Desktop，或者只在 README 里给 Dockerfile 并用 `docker build` 在别的机器上验证）。
> **面试时的诚实说法**："我用 uvicorn 在本地跑通了服务，Dockerfile 写好了，但本机没装 Docker，容器化是在【某处】验证的。"

```
│  ├─ generation/            提示词 + LLM 调用 + 结构化输出校验

├─ requirements.txt
└─ Dockerfile
```

## 10. 四周推进节奏（每周都有可交付物）

| 周 | 目标 | 交付物 |
|---|---|---|
| **W1** | 切分跑通 + 索引建起来 | `build_index` 能跑；能打印出带 `section_path` 的 chunk |
| **W2** | 检索跑通（纯向量 → 混合检索） | 命令行能问答；有引用输出 |
| **W3** | 评测集 + 第一次量化 | `eval` 输出 Hit Rate / 答对率；**第一组数据进迭代日志** |
| **W4** | API + 前端 + 部署 + README | 能在浏览器里流式对话；Dockerfile；GitHub 仓库可访问 |

> ⚠️ **W3 的评测数据是整个项目的核心资产**。没有它，这个项目在面试里就是"我做过一个 RAG"；
> 有它，就是"我把答对率从 X% 提到了 Y%"。
